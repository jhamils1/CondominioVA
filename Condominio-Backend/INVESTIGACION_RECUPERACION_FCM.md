# Alternativas para recuperar un cambio de cuenta con resultado FCM incierto

Investigación realizada el 31 de octubre de 2026 con documentación oficial y revisión del código instalado. No se ejecutaron llamadas a Firebase, no se enviaron mensajes y no se accedió ni cambió el teléfono o la base real.

## Hallazgos aplicables al proyecto

El proyecto declara `firebase_messaging` 16.0.4. En el código instalado, `deleteToken()` no recibe el identificador que debe invalidar; el adaptador Android llama a Firebase sin ese parámetro. El servicio actual obtiene tokens al iniciar y escucha renovaciones, y la coordinación de cambio de cuenta todavía no está integrada con ese servicio.

La documentación Android indica que, si la inicialización automática está activa, puede generarse un nuevo token al iniciar la app. Desactivarla es una pieza de coordinación, no una prueba por sí sola de que una operación perdida afectó al token esperado. La documentación actual de Android marca los métodos de tokens como obsoletos y recomienda nuevas API basadas en identificadores de instalación; esto no demuestra que la versión Flutter instalada ya exponga esas API. Debe comprobarse compatibilidad antes de migrar. [Referencia Android de Firebase Messaging](https://firebase.google.com/docs/reference/android/com/google/firebase/messaging/FirebaseMessaging) y [guía de inicio de FCM para Android](https://firebase.google.com/docs/cloud-messaging/android/get-started).

La aplicación de servidor ya ofrece baja idempotente de un registro propio, rechaza reclamar tokens de otras cuentas y mantiene inactivos los registros reservados. El procesador de alertas vuelve a comprobar destinatario, estado y token antes de enviar, pero una baja no retira un envío ya iniciado o aceptado. Tampoco prueba que no haya existido un token anterior desconocido o un envío por un camino distinto.

## Alternativas examinadas

| Alternativa | Qué aporta | Límites y decisión |
| --- | --- | --- |
| Mantener el estado incierto y usar la bandeja interna | Evita registrar automáticamente el push conflictivo para la nueva cuenta. | Es la opción segura actual. La disponibilidad de la bandeja con este estado integrado debe probarse; la coordinación aún no está conectada a la app. |
| Baja en el backend con la cuenta anterior | Impide que las rutas de envío que respetan el estado seleccionen ese registro activo. | Requiere autenticar a la cuenta titular y conocer sus identificadores; no invalida Firebase ni revoca mensajes en curso. No corresponde modificar el registro cuya titularidad no está aclarada. |
| Validación `dry_run` del Admin SDK | Firebase documenta una validación que emula el envío sin entregar el mensaje. | Sigue siendo una solicitud real a Firebase con credenciales y un identificador. No demuestra titularidad, ausencia de otros tokens ni el resultado exacto de una operación perdida. Un resultado exitoso no prueba que un usuario o teléfono sea el dueño; fallos transitorios o de credenciales no son prueba de invalidación. No se ha ejecutado. [Referencia de Firebase Admin para Python](https://firebase.google.com/docs/reference/admin/python/firebase_admin.messaging). |
| Respuesta `UNREGISTERED` | Firebase la documenta como señal de que el identificador de registro ya no es válido. | No atribuye la invalidación a una solicitud concreta, no prueba propiedad del teléfono ni resuelve tokens anteriores desconocidos. No se propone enviar un push para obtener esta señal. [Códigos de error de FCM](https://firebase.google.com/docs/cloud-messaging/error-codes). |
| Eliminar la instalación de Firebase desde el cliente | Podría permitir estudiar un reinicio más amplio de la identidad de la instalación. Firebase documenta la eliminación de la instalación mediante API cliente. | Afecta a servicios que utilizan ese identificador y puede generar otro posteriormente. Una respuesta perdida vuelve a crear incertidumbre. No demuestra titularidad ni garantiza por sí sola el tratamiento de todos los envíos y registros anteriores; requiere estudio de compatibilidad, consentimiento específico y pruebas aisladas. [Gestión de instalaciones de Firebase](https://firebase.google.com/docs/projects/manage-installations). |
| Eliminar la instalación desde el servidor | Existe una API administrativa para eliminar una instalación identificada. | Firebase advierte que los efectos pueden tardar y que la instalación aún puede recibir notificaciones durante un tiempo. Requiere identificar correctamente la instalación y autorización; no es apropiado para resolver el caso actual sin verificar la titularidad. [Gestión de instalaciones de Firebase](https://firebase.google.com/docs/projects/manage-installations). |
| API de registro por identificador de instalación | La documentación actual la presenta como dirección recomendada para la gestión de registros. | Es una posible evolución de arquitectura, no una solución lista para esta instalación. Requiere verificar versiones Android, Flutter, `fcm-django`, backend, compatibilidad y transición segura de registros existentes. [Buenas prácticas de gestión de registros FCM](https://firebase.google.com/docs/cloud-messaging/manage-tokens). |

## Recomendación y plan verificable

1. Mantener bloqueado el push conflictivo y no cambiar el dispositivo registrado de otra cuenta. Conservar la bandeja interna como alternativa, verificando este comportamiento cuando se integre el flujo.
2. Investigar en un proyecto Firebase y dispositivos de prueba separados qué versión y APIs están disponibles, qué evidencia devuelve cada operación y cómo se comportan las renovaciones, reinicios, caídas y respuestas perdidas. Una eventual llamada `dry_run`, aunque no entregue, usaría Firebase real y requiere autorización de esa etapa.
3. Diseñar recuperación solo después de definir una fuente verificable de evidencia, autorización de la cuenta anterior, coordinación entre procesos, inventario de registros conocidos y protección frente a envíos en curso. Tratar cualquier estado no demostrable como pendiente; no inferir la propiedad de una cuenta por el teléfono o por un cambio de token.
4. Revisar por separado la posible migración a identificadores de instalación y su compatibilidad de extremo a extremo. No modificar todavía el esquema o los registros existentes.

La investigación identifica opciones y límites; no demuestra que una alternativa permita recuperar automáticamente el caso actual. Para pruebas en el teléfono actual o acciones sobre el registro anterior se requiere identificar su titularidad y obtener autorización específica.
