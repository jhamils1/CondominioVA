Base de datos del condominio

19 tablas de negocio · 32 tablas totales · 35 relaciones · 207 columnas. Revisión: 28 de octubre de 2026.

Reconstrucción del esquema esperado a partir de las migraciones y modelos. No se consultó una base desplegada. Los tipos corresponden a PostgreSQL, indicado por la configuración de ejemplo.

Organización

Administración: persona, cargo y empleado. Residencial: habitantes, mascotas, visitas, objetos perdidos, áreas comunes, reservas, vehículos, bloques, unidades e incidentes. Finanzas: contratos, expensas y multas. Seguridad IA: lecturas de placas. Los paquetes restantes corresponden a infraestructura Django, JWT y FCM.

Cómo se relaciona

  • Un cargo tiene muchos empleados. Persona y empleado son tablas independientes; cada una puede enlazar opcionalmente con un usuario.
  • Inquilino, familiares y visitante heredan de persona: su persona_ptr_id es simultáneamente PK y FK. Una persona puede tener cero o una fila en cada subtipo. Inquilino tiene además un propietario; familiares tiene además una persona relacionada.
  • Un bloque contiene muchas unidades. Un contrato une una persona con una unidad; pueden existir varios contratos por persona y por unidad.
  • Una unidad tiene muchas expensas; una expensa tiene muchas multas. Un incidente puede apuntar a una persona y a una multa; ambos vínculos son opcionales.
  • Persona tiene vehículos y mascotas. Visita enlaza dos personas: visitante y quien recibe. Reserva enlaza persona y área común.
  • Lectura de placa puede vincularse a un vehículo; se admiten lecturas sin coincidencia. Objeto perdido puede vincularse a quien lo recibió.
  • Usuarios y grupos, usuarios y permisos, y grupos y permisos usan tablas intermedias para relaciones muchos a muchos.

Detalles importantes del esquema

  • No hay tablas propietario ni condominio: propietario se representa con persona.tipo=P.
  • La relación persona–unidad se obtiene mediante contrato. Inquilino no tiene FK directa a unidad.
  • No se declara unicidad de vehículo.placa, ni un único contrato activo por unidad, ni una restricción SQL que impida solapamientos de reservas.
  • unidad.codigo es único; también es única la pareja (bloque_id, numero). CI es único por separado en persona y empleado.
  • choices y limit_choices_to son reglas del ORM; no equivalen a CHECK SQL. blank controla validación, null controla nulabilidad.
  • on_delete describe el borrado gestionado por Django: cargo usa PROTECT, entregado_a usa SET_NULL y la mayoría de vínculos del negocio usan CASCADE. No se afirma que sean cláusulas SQL ON DELETE.
  • No se duplican en las tablas hijas las columnas heredadas de persona. Las asociaciones de herencia se representan como PK/FK uno a uno para reflejar la estructura relacional.

Importar en Enterprise Architect

  1. Crear o abrir un proyecto y seleccionar un paquete nuevo en el Browser.
  2. Usar Publish → Model Exchange → Import → XMI File (o Ctrl+Alt+I).
  3. Seleccionar condominio_base_datos.xmi e importar.
  4. Crear un diagrama de clases y arrastrar las clases de los paquetes; se mostrarán las asociaciones importadas. Aplicar distribución automática si hace falta.

El archivo usa UML 2.1 / XMI 2.1. Representa tablas como clases con columnas, tipos, cardinalidades y notas PK/FK/UNIQUE. No incluye posiciones de diagramas ni un perfil DDL nativo de Enterprise Architect. La validación automática comprueba XML, referencias, conteos y coincidencia entre modelos de negocio y migraciones.
